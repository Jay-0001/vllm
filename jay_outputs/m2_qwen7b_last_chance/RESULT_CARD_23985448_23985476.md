# Qwen7B final Q/K screen: first run

## Verdict

**Inconclusive.** The current deployed model and the isolated current-commit
Inductor region both emit separate Q and K RoPE kernels. The proposed combined
Triton kernel did not compile, so there are no correctness checks, oracle
timings, or downstream comparisons. This run cannot establish compiler regret
or close the M2 hypothesis on performance grounds.

## What completed

- Full-model compile job `23985448` used Git head
  `b98f392f6f7489b56bc325715c092172f476986e`, PyTorch `2.14.0+cu132`,
  and an A100-SXM4-40GB. The generated `model__1_inference_1.1/output_code.py`
  writes QKV in one external `addmm` (line 1109), then launches separate K
  and Q RoPE kernels (lines 1120 and 1126). Both read `buf9`.
- The same full-model job measured 131.06 ms mean latency over only two
  iterations. That number describes the baseline request, with no oracle arm
  and too few samples for a performance comparison.
- The isolated baseline compiled for decode shape 1 and prefill shape 512.
  Each generated wrapper has two RoPE `.run(...)` calls and returns V as a
  view of QKV. The jobs stopped before shapes 4 and 2048.

## Failure and correction

Array jobs `23985477` (decode) and `23985476` (prefill) each stopped after
about 42 seconds. Triton 3.8.0 raised `NameError: Cannot access global
variable QK_WIDTH from within @jit'ed function` while compiling the combined
kernel. This is a benchmark-code defect, not evidence that the alternative is
illegal or slower. The kernel now receives its dimensions as `tl.constexpr`
arguments. No numerical or latency claim follows until a rerun completes.

## Decision gate

Rerun only `jay_scripts/m2_qwen7b_qk_rope_oracle.sbatch` from the updated
checkout. Confirm all four shapes produce `result.json`, compare generated
launch counts, output errors, and paired CUDA graph replay timings. A measured
combined-kernel win on at least two shapes is required before considering
serving replay; a loss or equivalence closes this bounded Q/K candidate.
